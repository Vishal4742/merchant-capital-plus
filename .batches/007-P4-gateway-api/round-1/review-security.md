## HIGH

### H1. The voucher usage limit isn't enforced on money, so payers can bypass it at will (FR-GW-12)
- **Where:** `apps/web/lib/server/vouchers.ts:166` (the "used up" check at apply time reads only `times_redeemed`), `:191-197` (the reservation insert has no limit guard), `:207-218` (the only guard runs at confirm, after the payment has settled). The test codifies the gap: `apps/web/test/gw-vouchers.test.mjs:261` asserts `"reservations don't count"`.
- **Exploit:** the merchant creates `LAUNCH50` with `max_redemptions: 1` (or 10, "first 10 customers"). The attacker opens N checkouts from the merchant's page (20/min per IP per instance) and applies the code to each one. Every apply succeeds, because `times_redeemed` is still 0. Then the attacker pays all N at 50% off. `confirmRedemption` counts one use and marks the rest confirmed with nothing counted, but by then they've already paid the discounted price. Nothing stops this, and the attacker controls the timing; ordinary concurrent shoppers oversell the same way. The merchant's loss is N × discount, with no ceiling. Not reachable yet (claude-frontend's `POST /api/v1/sessions/:id/voucher` isn't wired), but that route will call this library as written.
- **Fix (owner: claude-contracts, Builder B's file):** count live holds against the limit at apply time, in the reservation statement itself. Insert or update only `WHERE times_redeemed + (unconfirmed reservations for this voucher, other sessions, created_at > now − SESSION_TTL_MS) < max_redemptions`. `SESSION_TTL_MS` comes from `lib/sessions.ts`, so an abandoned checkout frees its use after 30 min. Keep the confirm-time guard. Change the test at :261 to expect the second apply on a 1-use code to be refused, and to succeed again once the first hold has expired. Any oversell left is a millisecond race between two concurrent applies, not something an attacker can drive. For an exact limit, use a `times_held` counter on the voucher row (`UPDATE … SET times_held = times_held + 1 WHERE times_redeemed + times_held < max_redemptions RETURNING`). If the human would rather keep confirm-time counting as a product choice, they have to accept unbounded oversell explicitly (NEEDS THE USER). It can't stay a silent `ponytail:`.

## Checked and OK
- **SQL injection:** every query uses `$n` parameters. The only interpolations are constants (`COLUMNS`, `DELIVERY_COLUMNS`, `MAX_LIST`); `ANY($2)` gets an array parameter.
- **AuthN/AuthZ:** every dashboard route calls `signedInMerchant` first. Every mutation and lookup is `WHERE id = $1 AND merchant = $2`, so another merchant's id gets a 404 (keys, links, vouchers, webhooks, test, replay). Reports and settlements use the cookie's merchant only, plus a decoded `merchant` check on each log. Public routes go by a 59-bit random slug and return render fields only (no address beyond the short form, no `reference_id`). The cookie is `HttpOnly; SameSite=Lax` and there are no CORS headers, so cross-site POSTs carry no session and responses can't be read cross-origin. Dispatch compares `CRON_SECRET` as sha256 digests with `timingSafeEqual`; 503 when it's unset.
- **API keys:** 192-bit random, only the SHA-256 is stored, shown once, revoked keys filtered in SQL, GET returns no key or hash, the prefix exposes 4 random chars.
- **Webhooks:** https only, credentials refused, a check after DNS resolution (A+AAAA) on create and before every attempt, `redirect: "manual"`, 5 s timeout, response body cancelled unread, nothing about the URL logged. I verified IPv4-mapped and odd forms with Node 26 `BlockList`: `[::ffff:127.0.0.1]`, `[::ffff:a9fe:a9fe]`, `0x7f.1`, `2130706433`, `[64:ff9b::a9fe:a9fe]`, `[::]`, `[::1]` are all blocked. Signature is `t=…,v1=HMAC(secret, "t.body")` with a fresh `t` per attempt; the SDK's `constructEvent` uses a 300 s tolerance and `timingSafeEqual`. The secret is 256-bit and never appears in GET responses, logs or delivery JSON.
- **Vouchers (apart from H1):** they apply only to link/page sessions (no checkout row means refused, so a shop's sk_ session can't take one). They're bound to the checkout's merchant. The discount is taken off the recorded checkout amount, and the caller's amount must match it, so discounts can't stack. Re-applying replaces the code; paid checkouts are refused; the total must stay ≥ 1 USDT; percent discounts round down. The confirm UPDATE re-checks under the row lock, so exactly one concurrent confirm counts the last use.
- **Price tampering:** fixed links use the stored amount. Pages use stored item prices (unique names, qty 1..100, ≤ 20 lines). Open amounts are held to the page's min/max and the 1..1,000 USDT total. FX rounds up per item before multiplying by qty, and quotes round up, so rounding favours the merchant everywhere.
- **Secrets:** `handle()` logs only `err.name`; Arkiv errors go through `redactArkivError`; `migrate.mjs` prints table names only; nothing secret is returned except a new key or webhook secret, once, to its owner.
- **FR-ARK-4:** the `mcplus.voucher.v1` entity holds type, merchant (the business wallet, already public in `Paid` logs), `code_hash` = HMAC(VOUCHER_HASH_SECRET, merchant:code), kind, value and expires_at. No plain code, no payer data.
- **Errors:** `{error}` with fixed text, no stacks. CSV fields are numbers, addresses and hashes only, all quoted (no formula injection); the filename is built from validated dates.
