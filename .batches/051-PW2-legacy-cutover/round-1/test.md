## Findings (none blocks the batch's own scope; 2 and 3 should be fixed in this lane)
1. **medium, pre-existing.** apps/web/app/merchant/connections/page.tsx:83 (with the `<pre>` at :120). At 360 and 375 the page is 468 px wide for every role. The grid track grows to the `<pre>`'s min-content width because the `grid gap-8` container's children have no `min-w-0`, so `overflow-x-auto` on the `<pre>` never engages. For the Viewer, the new "Only Owners…" line is also 452 px wide and runs past the screen edge. Fix: `grid-cols-[minmax(0,1fr)]` on the container (or `min-w-0` on the MCP section). The file is in this batch's list.
2. **medium (spec deviation).** apps/web/components/workspace/LegacyAccess.tsx:9, :89. Wallet errors go through `walletError` from lib/merchant-wallet, which is copy for transactions. Spec C says `lib/onboarding` `walletProblem`. As a result, a pending request (-32002) or any non-rejection signing error says "Your wallet couldn't send this. Check it has a little WBT for fees". That contradicts "no transaction, no funds move", and a -32002 user needs to be told to close the open request. Fix: use `walletProblem(e, "sign")`, or a link-specific mapping (4001 → "You cancelled in your wallet. Nothing was signed."; -32002 → "Your wallet already has a request open…"; else "Your wallet couldn't sign the link message. Try again.").
3. **medium.** apps/web/components/workspace/LegacyAccess.tsx:171. `WorkspaceSignOut` swallows a failed `POST /api/v2/auth/signout` and still redirects to `/sign-in?out=1`. The session stays live and the cookie stays set, so on a shared computer the dashboard reopens. Scenario: x-signout-failed. Fix: on a non-OK answer, stay on the page and show "We couldn't sign you out. Try again." (`role="alert"`). Alternatively, have `/sign-in?out=1` retry the server sign-out. The same pattern is at apps/web/components/workspace/WorkspaceSettings.tsx:91 (owner: whiteflow-f3).
4. **medium.** apps/web/components/gateway/Links.tsx:78–121 (links page), and the same applies to pages and vouchers. A Viewer of a linked workspace sees the full "New payment link" form, "Create link" and "No links yet. Create one above". Submitting returns 403 "Your role in this workspace can't do that." The server holds, but the UI offers an action the role can't take. The Overview's "Create a link" step and Quick actions (app/merchant/page.tsx:270) are offered to a Viewer the same way. Fix: pass `scopes` from `currentWorkspace()` and disable these controls with a visible reason, as f3's Settings does ("Only an Owner can …"). This could be a follow-up batch, since spec C keeps the UI minimal.
5. **low-medium (a11y regression).** apps/web/components/workspace/LegacyAccess.tsx:176. The new "Sign out" control is 46×16 px. The SIWE `SignOut` it replaces used `Button variant="quiet"` (`min-h-11`, 44 px). 16 px is below the WCAG 2.2 2.5.8 minimum of 24 px. Fix: `buttonClasses("quiet")` from `@/components/Button` (no import cycle with Frame), or `inline-flex min-h-10 items-center`.

## UX/UI review
Copy clarity
- **medium.** components/workspace/LegacyAccess.tsx:148 "Link your **existing** merchant wallet … Its links, pages, vouchers, keys, webhooks and payments **move into** this workspace". A new merchant without a legacy wallet gets no hint that any wallet they control will do, and every dashboard page is closed until one is linked. "Move into" sits right before "no funds move". Suggest: "Link the wallet you get paid with (the one you used on this dashboard before, if any). Its links, pages, keys, webhooks and payments will then be managed in Acme Studio by role. You sign one message: no transaction, no funds move."
- **low.** components/gateway/Frame.tsx:110 and :117–119. The hero says "Sign in to WhiteFlow to start." and the card intro says "Sign in to WhiteFlow, then link that wallet once". Both show to users who are already signed in (states b, c, d), and the signed-out card says "Sign in to WhiteFlow" three times. Suggest moving the intro into `LegacyAccess`'s signed-out branch and making the hero state-neutral ("Open your workspace to start.").
- **low.** components/workspace/LegacyAccess.tsx:141 "You're a Viewer: ask an Owner to link it." Clear. Naming an Owner (or pointing to Settings → Team) would make it actionable.
- **low.** app/merchant/developers/page.tsx:82 vs app/merchant/connections/page.tsx:136. The same "Only Owners…" sentence is 16 px on one page and `text-sm` on the other. Use one size, and consider adding who the Owners are, or "Ask an Owner for a key."

Consistency with the dashboard
- **low.** components/gateway/Frame.tsx:58–67. The account badge still shows only the legacy wallet (`0xabF4…999b`). The session is now a WhiteFlow workspace with a name and a role, and the Overview band says "YOUR WORKSPACE". Suggest "Bandra Beans Co · Owner" with the wallet as secondary text.
- **low.** components/workspace/LegacyAccess.tsx:18–21. Local `primary` and `secondary` class strings duplicate `components/Button` (`h-11` here vs `h-12` primary there). The cycle the comment worries about only applies to Frame, not Button. Suggest `buttonClasses()`.
- **medium (owner: whiteflow-f3).** app/merchant/settings/page.tsx:56–59. For a signed-in Owner of an unlinked workspace, the only link entry on Settings is inside a collapsed `<details>` titled "Legacy dashboard sign-in (wallet)". It renders a whole second `PlainPage`: another wordmark header, the hero, and "Sign in to WhiteFlow to start." for a user who is signed in (c-settings-legacy-details-*). The label is also stale, since this is no longer a wallet sign-in. Suggest rendering just `<LegacyAccess />` in a "Merchant account" card, titled "Link your merchant wallet".
- **low (owner: whiteflow-f3).** app/merchant/settings/page.tsx:108–119, 239–241. For a linked Owner, Settings still says "Authentication Mechanism: Sign-In with Ethereum (SIWE)…" and shows the SIWE `SignOut`, which posts to the retired `/api/auth/logout` and doesn't revoke `wf_session`. "Multi-Role Access & Approvals … Stage 3 Planned … single-operator mode" is also outdated now that roles exist. These belong in the SIWE cleanup batch or an f3 follow-up.

Layout at 360 / 375 / 1440
- All panel states fit at 360 and 375. The card sits under the hero on mobile and to its right on desktop. The only overflow is finding 1. The 1440 card leaves a large empty area below it (the `dl` is in the left column). That's acceptable.

Accessibility
- **low.** components/workspace/LegacyAccess.tsx:154–158. The `aria-live="polite"` step paragraph is mounted together with its first text, so many screen readers won't announce "Choose the merchant wallet…". Suggest always rendering the live container and only changing its text.
- **low.** components/workspace/LegacyAccess.tsx:151. The button becomes `disabled` while focused, so keyboard focus drops to `<body>` mid-flow. Suggest `aria-disabled` plus `aria-busy`, ignoring clicks while busy (the shared `Button` already does this).
- **low.** components/workspace/LegacyAccess.tsx:93. The loading line has no `role="status"`. That's acceptable since it is brief.
- Error and problem text use `role="alert"`, and the down state wraps its sentence and "Try again" in `role="alert"`. Contrast on the white card is fine: body and intro text rgb(90,92,110) 6.58:1, error rgb(192,53,42) 5.55:1, links rgb(59,79,217) 6.35:1. Focus outlines are visible on every panel control (i).
- **low, noise.** Signed-out pages log "Failed to load resource: 401" (twice in dev) because `GET /api/v2/legacy` uses 401 to mean signed out, as the spec says. That's harmless. Just don't count these as errors in future walks.
